# Architecture refactor progress

This log records ownership decisions and validation for the production architecture refactor.

## Completed

| Module | Before | Actual responsibility | After | Reason | Tests | Remaining risk |
| --- | --- | --- | --- | --- | --- | --- |
| theme composition | Shared package exposed the client `ThemeData` and a selectable appearance surface | Client palette, typography, semantic colors, and generic UI styling | Each client owns `src/app/theme/app_theme.dart` and exposes only `AppTheme.data`; design_system retains semantic tokens and generic context helpers | Keep the default appearance app-local without creating a shared theme or selection API | Design-system suite: 17 passed; Passenger and Driver app-theme suites: 3 passed each | Final monorepo validation should confirm no shared `ThemeData` remains |
| foundation | `shared_core` mixed generic infrastructure with app/domain exports | Generic failures, lifecycle, network, realtime, and route-payload utilities | `foundation` owns the technical subset and all app consumers import it directly | Give technical dependencies a focused shared owner | Foundation tests passed; both app analyses have no errors | Review app-wide infrastructure placement during the `core` migration |
| maps | Map/location capability was mixed into `shared_core` and app-local duplicates | Provider/platform map, location, geocoding, and route capability | `maps` owns the shared provider boundary | Both apps use the same provider capability without sharing workflow state | Maps package tests passed | Review app-specific map behavior still importing shared helpers |
| app infrastructure | Each client kept configuration, transport, session, telemetry, and unrelated helpers under `src/core` | App-wide external-system adapters versus feature-owned validation and presentation formatting | Each client now owns config, API client/interceptor, session store, storage keys, and background telemetry under `src/infrastructure`; auth endpoints and helpers live with their features; `src/core` and dead `SecureStorage` adapters were removed | Make the application boundary explicit without turning infrastructure into a product-feature dumping ground | Passenger client: 178 passed; Driver client: 106 passed; both analyses report no errors or warnings | Final import and structure audit only |
| shared core models | `shared_core` exposed generic foundation exports plus Driver, Profile, and Notification models | Passenger nearby-driver discovery and each client’s profile workflows | Passenger booking owns `DriverModel`, each profile feature owns `ProfileModel`, unused notifications were removed, and `shared_core` was deleted | Remove the compatibility package and keep product models with their owning features | Passenger profile/booking tests passed; Driver profile tests passed; both analyses have no errors | Final import and structure audit only |
| passenger booking and active ride | Passenger `trip` mixed booking and accepted-ride tracking | Booking, driver discovery, fare display, offers, and draft state versus live tracking and driver match | `booking` and `active_ride` feature boundaries | Make the passenger lifecycle explicit and independently navigable | Passenger app tests: 165 passed | Final route and import audit only |
| driver active ride | Driver `trip` contained the accepted-ride lifecycle | Dispatch acceptance, pickup, passenger wait, transit, telemetry, and fare summary | `active_ride` feature boundary | Match the business concept used by the server and passenger app | Driver app tests: 90 passed; analysis clean | Final route and import audit only |
| auth | Shared package provided transport contracts, failures, and presentation events while apps owned role-specific repositories | Authentication transport, failures, credentials, repositories, and presentation state | Passenger and Driver auth features own their complete workflows; `packages/auth` removed | Keep authentication changes role-specific and remove product behavior from shared packages | Passenger auth: 22 passed; Driver auth: 7 passed | Final import audit only |
| chat | Shared package owned chat entities, repository, failure, and transport | Chat room lifecycle, message protocol, websocket reconnect, and presentation state | Passenger and Driver `chat` features own their data, domain, repository, factory, and tests; `packages/chat` removed | Keep chat as a product workflow while leaving only generic transport candidates for shared infrastructure | Passenger chat: 12 passed; Driver chat: 12 passed; Passenger analysis has no errors; Driver analysis clean | Generic event hub and chat room hub are now separated; final tests remain |
| ride | Shared package owned ride entities, DTOs, fare structures, and workflow failures | Passenger booking/fare/history contracts and Driver active-ride lifecycle contracts | Passenger booking, activity, and active-ride features plus Driver active-ride own the required contracts; `packages/ride` removed | Keep client workflows local while the server remains authoritative for fare and ride rules | Passenger affected features: 95 passed; Driver affected features: 42 passed; both analyses have no errors | Final import audit only |
| repository contracts | `i_*` domain contracts and ambiguous concrete repository filenames | Domain interfaces and feature data implementations | Meaningful boundaries use `domain/repositories/<feature>_repository.dart` with `<Feature>Repository` and `data/repositories/<feature>_repository_impl.dart` with `<Feature>RepositoryImpl`; simple stores remain concrete | Make contracts and implementations searchable while avoiding repository ceremony for trivial features | Passenger: 178 passed; Driver: 107 passed; no legacy `i_` repository references | Maps data source remains a provider adapter, not a repository implementation |
| passenger ride history | Passenger `activity` combined history, details, payment, rating, and recent-ride concerns | Historical ride browsing and associated presentation flows | `features/ride_history` owns the history module, repository, entities, BLoC, views, and widgets; booking retains destination-map behavior | Give history a business-facing feature boundary while preserving existing deep-link paths | Passenger app: 178 passed; analysis has no errors | Existing user-facing Activity labels and API endpoint names remain for compatibility |
| Ent schema ownership | Feature packages duplicated schema files alongside the generated Ent aggregate | Canonical persistence schema and generated client | `internal/platform/ent/schema` is the sole schema source; `cmd/entgenerate` generates from it without copying files | Keep persistence ownership singular and protect generated output from hand edits | Ent generation, platform migration tests, build, and vet passed | Final generation diff check only |
| server application layers | Backend packages used `usecase` for application behavior | Application services and orchestration | All backend `usecase` directories and package declarations are named `application` | Make the architecture layer explicit without changing service behavior | Build, vet, focused application tests, and compile-only package tests passed | Final import audit only |
| server capability packages | Backend business packages were pluralized as `rides` and `users` | One ride capability and one user capability | `internal/ride` and `internal/user` own those capabilities; routes and database table names are unchanged | Use singular package names consistently with the capability model | Build, vet, and focused ride/user tests passed | Final import audit only |
| realtime ownership | Generic event streaming and chat room websockets shared the ambiguous `realtime/stream` and `realtime/ws` layout | Generic topic hub versus chat room protocol | Generic hub lives in `internal/realtime/hub`; chat room websocket code lives in `internal/realtime/chat/transport/ws` with `RoomHub` | Keep protocols and ownership explicit while preserving route behavior | Realtime focused tests, build, vet, and compile-only package tests passed | Full websocket tests require host socket permission in restricted environments |
| server test topology | Unit and HTTP contract tests were mixed under `server/tests` | Source-owned unit coverage versus environment-dependent integration coverage | Unit tests live beside source packages; HTTP suites live under `server/integration` with the `integration` build tag; `server/tests` is empty | Make test scope and runtime dependencies visible | Tagged integration compile and integration suite passed; focused unit tests passed | Final full default and tagged runs remain |
| backend CI coverage | CI ran only untagged backend tests after integration suites received a build tag | Default unit checks plus explicit integration checks | Justfile and GitHub Actions run normal and race-detector tests with `-tags=integration` | Ensure classified integration coverage remains part of the quality gate | `git diff --check` passed | Hosted race/integration runtime is the final external validation |
