# Repository Instructions

## Project Map and Sources of Truth

- This repository contains Flutter apps in `apps/driver` and `apps/passenger`, shared Dart packages in `packages/{core_domain,design_system,foundation,maps,shared_pages}`, the Go module in `server`, and a separate SvelteKit admin app in `web/admin`.
- The Flutter apps organize features under `lib/src/features/<feature>` with `data`, `domain`, and `presentation` layers. They use `flutter_bloc` and `go_router_modular`; continue the local feature pattern and use BLoC/Cubit for feature state already modeled that way.
- The Go backend is a modular monolith under `server/internal`. Preserve each module's existing domain, application, ports, adapter, and transport boundaries. `server/internal/app` is the composition root.
- PostgreSQL query and schema sources are under `server/db/{queries,schema}`; migrations are under `server/db/migrations`; `server/internal/platform/database/sqlc` is generated by sqlc. Edit source queries/schema and migrations as needed, regenerate with `cd server && go tool sqlc generate`, and do not hand-edit generated files.
- CI pins Flutter 3.47.2, which bundles Dart 3.13.2; app and package manifests require Dart 3.13.0 or newer within their declared SDK ranges. `server/go.mod` declares Go 1.27.0. Keep syntax and APIs within the repository's SDK constraints and locked dependency versions.
- Use `melos.yaml`, package manifests, `server/go.mod`, `web/admin/package.json`, `justfile`, CI workflows, and current source for package boundaries and commands. Consult `architecture/README.md` for design context when changing mobile layers, backend modules, persistence/security, real-time flows, or shared packages; verify diagram details against code because overview docs and generic skills may lag.
- Read applicable skills from `.agents/skills` and enabled Codex plugins before using them. Check their assumptions against the current manifests and code, and preserve established project conventions.

## MCP Usage

- Check which MCP tools are actually exposed in the current Codex session before relying on them; a server listed in Codex configuration may not be available to this session.
- Automatically use `dart-mcp-server` for relevant Dart/Flutter language analysis, diagnostics, code navigation/refactoring, or widget/runtime workflows when the matching tool is available.
- Automatically use `gopls` for relevant Go definitions, references, call relationships, diagnostics, and refactoring when the matching tool is available.
- Prefer language-aware MCP results over text-only inspection when they are more reliable. Use `rg` and file inspection for literal searches, discovery, or when MCP tools are unavailable.
- Use Context7 or another documentation MCP only when it is available and current external documentation is needed. Do not make repeated or redundant MCP calls, and never claim a tool was used unless it was.
- Fall back to the repository's SDK and CLI tools when an MCP server or operation is unavailable. Keep MCP installation and connection settings in Codex configuration, not this file.

## Dart and Flutter

- Follow each app's `analysis_options.yaml`, package imports, formatter, and existing BLoC/Cubit patterns. Keep feature UI, state, domain behavior, and data access in their established layers; use `packages/design_system` for shared tokens and widgets.
- Prefer sound null safety, explicit types, immutable state, and `const`/`final` where appropriate. Choose newer Dart features only when supported by the SDK constraints and clearer than the existing pattern.
- Keep asynchronous work lifecycle-safe: guard `BuildContext` use after awaits, cancel subscriptions, and dispose controllers in their owning state. Avoid unnecessary widget rebuilds and new abstractions.
- Test behavior at the narrowest useful level with the existing Flutter test setup; add widget or integration tests when the changed user-visible behavior needs them.

## Go

- Follow idiomatic Go naming and `gofmt`. Pass `context.Context` through request, database, and external I/O paths; wrap errors with useful operation context; preserve cancellation and goroutine ownership.
- Keep interfaces at meaningful module or infrastructure boundaries. Avoid adding an interface for every concrete type or adding layers that do not clarify ownership.
- Validate untrusted input and enforce authorization at server boundaries. Preserve transaction, locking, idempotency, and lifecycle invariants when changing persistence or request flows.
- Keep SQL parameterized through sqlc. Update schema, queries, migrations, generated code, and tests as one coherent change; use migrations for database changes and regenerate sqlc output through the configured tool.
- Add focused tests for changed behavior and preserve the unit/integration split; integration tests use the `integration` build tag and require their services.

## Security and Change Scope

- Preserve API contracts and security checks. Root `.env` values belong to the Go service and Compose workflows; app `.env` files are bundled public configuration and must not contain backend credentials.
- Before removing code, verify references, route or runtime registration, generated usage, reflection, and external integration points.
- Make focused changes and avoid unrelated formatting or refactoring. Do not edit generated files directly or expose secrets in code, logs, or command output.

## Validation Commands

Run focused checks for affected files or packages first, then the nearest broader gate. Do not run expensive integration or full-workspace suites for unrelated changes.

### Flutter and Dart

- `just bootstrap` after dependency or workspace manifest changes.
- Run `dart format` on changed Dart files; use `dart format --set-exit-if-changed apps packages` to check the workspace.
- From the affected app or package, use `flutter analyze --no-fatal-infos .` and `flutter test` (with a test file path to narrow it) as focused checks.
- `just analyze` runs the Melos workspace analyzer. `just ci-flutter` runs the broader local Flutter gate; `dart run melos exec -- "flutter test --reporter compact"` runs tests across Melos apps and packages as in CI.

### Go

- From `server`, run `gofmt -w` on changed Go files, then use `go test ./internal/ride/application` (replace with the affected package), `go vet ./...`, or `go build ./...` as appropriate.
- `just server-unit` runs all Go unit tests; `just server-race` runs the race-enabled suite.
- `just ci-backend` is the broader backend gate, including sqlc, vet, race, and integration tests; use it when the change warrants those checks and required services are available.

### Admin and Repository

- In `web/admin`, use `bun run check`, `bun run test`, and `bun run build` as appropriate. This app is separate from the Melos workspace.
- `just ci-guards` runs `git diff --check`. Use the commands in `justfile` and `.github/workflows/ci.yml` as the source for additional project checks.
